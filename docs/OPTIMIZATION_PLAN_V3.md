## 〇、产品定位（用户明确）

**就两件事：① 自动爬招考公告 + 提取结构化数据；② 网站展示 + 筛选 + 详情。**

一切功能围绕这两件事服务，不做花活。数据要准（已有 LLM 提取 + 规则校验 + 审计闭环），展示要清晰。

## 一、反馈系统（用户新增需求）

### 1.1 详情页「纠错反馈」——极简版

**交互**（详情页底部，紧接"查看原文"）：

```
┌────────────────────────────────────────────┐
│  发现信息有误？                              │
│  [ 备注（必填，最多 500 字）                  │
│    ▸ 原文写的是7月24日截止，这里写的是7月7日… │
│  ]                                          │
│  [ 提交反馈 ]                                │
└────────────────────────────────────────────┘
```

**设计决策（用户拍板）**：
- ❌ 不做"哪个字段错了"的多选框——**就一个备注框**，用户直接写
- ❌ 不做验证码——**裸奔**
- ✅ 限频：**同一 IP 一分钟最多 1 次**（D1 查最近记录判断）
- ✅ 自动绑定：`announcement_id` + `title` 由前端隐藏携带，用户不用填
- ✅ 联系方式：可省（不强制），做了就留一个选填框

**技术设计**：
| 项 | 设计 |
|---|---|
| 后端 | 复用 `/api/feedback`（type 固定传 `data_error`），扩展 `announcement_id` |
| 数据库 | `user_feedback` 加列：`announcement_id INTEGER`、`contact TEXT` |
| 限频 | 同 IP 60 秒内重复提交 → 429；实现：查 `user_feedback` 最近一条的 `created_at` + 记录来源 IP（加 `ip TEXT` 列） |
| 处理闭环 | pending → 运营后台核对原文 → resolved（修正数据）/ rejected（无误） |

### 1.2 全站「反馈中心」——需求反馈 + 网站提交 二合一

**交互**（导航栏「反馈」→ 弹窗，两 Tab）：

```
┌────────────────────────────────────────────┐
│  反馈中心                              ✕      │
│  [ 提建议 ] [ 推荐网站 ]                      │
│                                            │
│  ── 提建议 ──                                │
│  你的建议（必填，最多 2000 字）：              │
│  [ 希望能按省份筛选…                        ] │
│  [ 提交 ]                                   │
│                                            │
│  ── 推荐网站 ──                              │
│  网站名称（必填）：[ 浙江省人事考试网       ]  │
│  网站地址（必填）：[ http://zjks.com/      ]  │
│  [ 提交 ]                                   │
└────────────────────────────────────────────┘
```

**技术设计**：
| 项 | 设计 |
|---|---|
| 类型映射 | 提建议 → `feature_request`；推荐网站 → `new_website` |
| 复用 | 完全复用 `/api/feedback` + `user_feedback` 表，**零后端新端点** |
| 限频 | 同样 IP 一分钟 1 次（与详情页共用限频逻辑） |
| about 页 | 现有"提交新网站"入口改为统一跳反馈中心 |

### 1.3 反馈处理后台（隐藏页 + token）

**形态**：`/admin/feedback` 隐藏页，URL 带 token（如 `/admin/feedback?token=xxx`）或 Header 校验，不做登录系统。

**能力**：
| 能力 | 说明 |
|---|---|
| 反馈列表 | 按状态 × 类型筛选，标注来源公告标题 |
| 一键跳转 | 从反馈直达对应公告详情页（`announcement_id` 关联） |
| 数据修正 | 确认错误 → 更新 announcements 对应字段 → 标记 resolved |
| 导出 | 反馈 CSV（含公告标题/时间/内容） |

## 二、考情产品化（对照辅导员大表，仅保留展示层增强）

> 只做"展示得更清楚"的事，不做新业务。辅导员大表的信息密度 → 我们页面清晰呈现。

### 2.1 保留的场景映射

| 辅导员用法 | 网站增强 | 说明 |
|---|---|---|
| 滚动补录（报名/笔试/出分回填） | **进度状态推导** | 从现有字段自动算：报名截止日过了=报名结束、笔试日过了=已出分。**零新增爬虫** |
| 目录导航（按类型分区） | 首页考试类型 Tab + 地区筛选（已有）+ 科目筛选（P0 补） | 已有基础，补科目 |
| 暗语系统（未知/——/无） | 前端区分显示 | examNote 已有三态，缺失值区分"未公布/无" |
| 对比分析背书 | 详情页近 3 年公告时间线对比（可选） | 需要历年数据支撑，**P2 评估后定** |

### 2.2 砍掉/不做的（用户决策）

| 功能 | 结论 | 理由 |
|---|---|---|
| 咨询助手（LLM 对话） | ❌ 砍掉 | 用户：不需要过于进阶 |
| 推送提醒（报名/笔试倒计时） | ❌ 砍掉 | 用户：没必要 |
| 政策差异库（19 问×省） | ⏸ 暂缓 | 需人工整理数据源，非"展示"范畴，等有需要再说 |
| 考试聚合（后续公告关联成时间线） | ⏸ 暂缓 | 属于进阶数据能力，当前笔试日期"另行通知"是原文客观状态，非产品缺陷 |

## 四、反馈系统数据流

```
用户（详情页/反馈中心）→ 提交 {announcement_id?, type, content}
     ↓ POST /api/feedback（IP 60s 限频）
user_feedback 表（status=pending, 记录 ip/announcement_id）
     ↓ 运营后台（P0-04）核对原文
确认错误 → UPDATE announcements → status=resolved
     ↓
（可选）每周导出反馈 CSV 看哪些公告被纠错最多
```
