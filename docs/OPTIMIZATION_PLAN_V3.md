## 一、用户新增需求设计

### 1.1 详情页「纠错反馈」（数据纠错闭环）

**产品价值**：考情数据由爬虫+AI 生成，难免有错。让每一个浏览者成为"免费校对员"，数据越用越准。这是**众包校对**——辅导员大表靠人工录，我们靠用户纠错。

**交互设计**（详情页底部，紧接"查看原文"）：

```
┌────────────────────────────────────────────┐
│  发现信息有误？告诉我们，帮大家把数据改对      │
│                                            │
│  我要反馈的问题：                             │
│  (•) 报名截止时间有误   ( ) 笔试时间有误       │
│  ( ) 科目有误          ( ) 人数有误           │
│  ( ) 考试类型有误      ( ) 其他错误            │
│                                            │
│  备注（选填，最多 500 字）：                  │
│  [ 原文写的是 7月24日截止，这里写的是7月7日… ] │
│                                            │
│  联系方式（选填）：[ 微信/邮箱                ]│
│  [ 提交反馈 ]                               │
└────────────────────────────────────────────┘
```

**技术设计**：

| 项 | 设计 |
|---|---|
| 绑定数据 | 自动携带 `announcement_id` + `title`，用户无需填 |
| 反馈字段 | 预定义 `data_error` 类型 + `error_field`（哪一列错了）+ `content` 备注 + `contact`（选填） |
| 后端 | 复用 `/api/feedback`，扩展 `announcement_id` 与 `error_field` 字段 |
| 数据库 | `user_feedback` 表加列：`announcement_id INTEGER`、`error_field TEXT`、`contact TEXT` |
| 处理闭环 | pending（待处理）→ 校对原文 → resolved（已修正并更新数据）/ rejected（无误） |
| 反哺机制 | 修正数据后，反馈记录打上 `processed_at`，形成"反馈→修正→入库"闭环 |

**为什么放详情页**：错误只会发生在具体某条数据上，上下文（原文 URL、当前字段值）都在详情页，用户反馈成本最低（无需解释是哪条数据）。

### 1.2 全站「反馈中心」——需求反馈 + 网站提交 二合一

**产品价值**：一个入口承接两类诉求——①用户想要的新功能（需求反馈）②用户发现的好网站（网站提交/扩源建议）。合并降低入口成本，让"反馈"成为网站增长引擎（扩源靠用户推荐）。

**交互设计**（页面顶部导航「反馈」→ 弹窗/页面）：

```
┌────────────────────────────────────────────┐
│  反馈中心                              ✕     │
│                                            │
│  [ 提需求 ] [ 推荐网站 ] ← 两个 Tab 二合一    │
│                                            │
│  ── 提需求 ──                               │
│  你的建议（必填，最多 2000 字）：             │
│  [ 希望能按省份筛选、能订阅笔试时间提醒… ]     │
│  联系方式（选填）：[                      ]  │
│                                            │
│  ── 推荐网站 ──                              │
│  网站名称（必填）：[ 浙江省人事考试网        ]  │
│  网站地址（必填）：[ http://zjks.com/      ]  │
│  说明（选填）：[ 这里有很多事业单位公告…    ]  │
│                                            │
│  [ 提交 ]                                   │
└────────────────────────────────────────────┘
```

**技术设计**：

| 项 | 设计 |
|---|---|
| 类型映射 | Tab1 提需求 → `feature_request`；Tab2 推荐网站 → `new_website` |
| 新网站字段 | `content` 存结构化文本："名称: xxx\n地址: xxx\n说明: xxx"，前端拼装 |
| 复用 | 完全复用 `/api/feedback` + `user_feedback` 表，零后端改动（仅前端新增入口） |
| 现有 about 页 | 已有的"提交新网站"入口改为统一跳转反馈中心，避免两处维护 |

**二合一的理由**：两者都是"用户告诉团队做什么"，只是对象不同（功能 vs 网站）。统一入口 → 统一处理队列 → 统一运营视图。

### 1.3 反馈运营后台（辅导员视角）

**产品价值**：反馈要有处理动作才算闭环。给运营/辅导员一个轻量后台：

| 能力 | 说明 |
|---|---|
| 反馈列表 | 按状态（待处理/已处理/已拒绝）× 类型筛选，标注来源公告 |
| 一键跳转 | 从反馈直达对应公告详情页（`announcement_id` 关联） |
| 数据修正 | 确认错误 → 更新 announcements 对应字段 → 自动标记反馈 resolved |
| 导出 | 每周反馈汇总 CSV（哪些字段错误最多 → 反哺提取规则） |

**反哺规则引擎**：如果某字段错误反馈 > 3 次，说明提取逻辑对该场景有系统性问题 → 触发规则/提示词优化（这是"数据质量监控"P3-03 的输入之一）。

## 二、考情产品化设计（对照辅导员大表场景）

> 辅导员大表的使用模式 = 我们产品的功能清单。逐条映射：

### 2.1 场景映射表

| 辅导员用法（大表） | 网站产品化（P2） | 优先级 |
|---|---|---|
| **目录导航**：按类型分区 + 置顶主推表 | 首页分类导航：考试类型 Tab（事业单位/公务员/三支一扶…）+ 热门考试置顶 | 🔴 高 |
| **滚动补录**：公告期填前半段，出分/面试后回填 | **进度状态自动推导**：已发布→报名中→已出分→已面试（从后续公告自动补录） | 🔴 高 |
| **表格即话术库**：政策问答直接照表答复 | **政策差异库**（19 问 × 省）：应届/学历/户籍/分卷 检索 | 🔴 高 |
| **对比分析背书**："去年 X 月出公告、备考 37 天" | **自动对比计算**：近 3 年公告时间线、备考周期、面试间隔 | 🟡 中 |
| **暗语系统**：——/未知/无 语义 | **缺失值四态**：known/unknown/na/none 前端区分渲染 | 🟡 中 |
| **资料链接**：职位表/指南/目录超链接 | **资料链接区**：exam_materials 表 + 详情页展示 | 🟡 中 |

| **是否告知排名**（咨询关键） | 详情页字段：成绩查询时间 + 是否告知排名 | 🟢 低 |
| **备注/话术笔记**（辅导员内部） | exam_notes 表（后期运营维护） | 🟢 低 |

## 四、反馈系统数据流（全链路）

```
用户（详情页）→ 提交纠错 {announcement_id, error_field, content}
     ↓ POST /api/feedback（Bearer 免鉴权，但限频）
user_feedback 表（status=pending）
     ↓ 运营后台（P1-06）查看，跳转详情核对原文
校对确认错误 → UPDATE announcements 修正字段
     ↓
status=resolved + processed_at + 记录修正值
     ↓
周报聚合：error_field 分布 → 若某字段错误率>阈值
     → 反哺规则引擎/提取提示词（P3-03）
```

## 五、待确认事项

1. **反馈是否需要登录**：不做登录（低门槛优先），靠限频（IP 每天 5 条）+ 内容校验防滥用？还是接 Cloudflare Turnstile 验证码？
2. **详情页纠错字段粒度**：只做"哪个字段错了"（简单，够用），还是做到"字段级 + 原值/建议值"（更准，但用户负担高）？我建议前者。
3. **反馈后台形态**：公开隐藏页（URL 直访 + token）还是纯内部脚本？我建议先做隐藏页 + 简单 token。
4. **进度状态推导**：报名中/待笔试等状态从现有字段推导（无新爬虫），是否够用？后续公告聚合（P1-05）才做完整时间线。
5. **P2-03 政策库初始数据**：19 问 × 省的政策答案从哪来？辅导员大表有部分，其余需人工整理首期覆盖 5 省。
